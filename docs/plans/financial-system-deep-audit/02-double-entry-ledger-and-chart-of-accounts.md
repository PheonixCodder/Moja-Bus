# Chapter 2: Double-Entry Ledger & Chart of Accounts

## 1. The Accounting Paradigm

Moja Bus implements a strict, audit-compliant **Double-Entry Bookkeeping Engine** implemented in TypeScript (`@moja/db/src/services/AccountingEngine.ts`) and backed by PostgreSQL tables.

### Key Principles:
1. **Duality**: Every financial event creates at least one DEBIT and at least one CREDIT entry.
2. **Equilibrium**: The sum of debits must exactly equal the sum of credits:
   $$\sum_{i} \text{Debit}_i = \sum_{j} \text{Credit}_j$$
3. **Safe Integer Precision**: All currency units are stored in whole integer units of Franc CFA (XOF) using `BigInt` columns in PostgreSQL and safe integers in Node.js.
4. **Immutability**: `LedgerEntry` records can never be updated or deleted. Corrections are posted as new reversing transactions (`REVERSED` / `VOIDED`).
5. **Atomic Balance Maintenance**: `postedBalance`, `reservedBalance`, and `availableBalance` on `FinancialAccount` are managed **exclusively** by the `AccountingEngine` within serializable transactions using PostgreSQL row-level locks (`SELECT ... FOR UPDATE`).

## 2. Chart of Accounts

The chart of accounts is organized by `AccountCategory` and `AccountOwnerType`:

### Standard Account Categories:
- **ASSET**: Resources owned or controlled by the system (e.g. money in Paystack). Debit increases (+), Credit decreases (-).
- **LIABILITY**: Obligations owed to external parties (passengers, operators). Credit increases (+), Debit decreases (-).
- **REVENUE**: Earnings generated by the platform. Credit increases (+), Debit decreases (-).
- **EXPENSE**: Costs incurred by the platform. Debit increases (+), Credit decreases (-).

### Complete Moja Bus Account Catalog:

| Account Class | Owner Type | Category | Default Owner ID | Description | Allow Neg? |
|---|---|---|---|---|---|
| `PAYSTACK_CLEARING` | `SYSTEM` | `ASSET` | `system` | Physical custodial fiat balance held at Paystack. Increased by card/Momo checkouts and wallet top-ups; decreased by payouts and fees. | **Yes** (temporary transit) |
| `PASSENGER_WALLET` | `USER` | `LIABILITY` | `<userId>` | Real cash funds owed to the passenger. Funded via top-ups or verified cash refunds. | **No** (cannot overdraw) |
| `PROMO_CREDITS` | `USER` | `LIABILITY` | `<userId>` | Promotional marketing credit balance owed to the passenger (earned from referrals/grants). | **No** |
| `OPERATOR_RECEIVABLE` | `COMPANY` | `LIABILITY` | `<companyId>` | Money owed by the platform to a bus operator. Holds both escrowed (`reservedBalance`) and cleared (`availableBalance`) funds. | **Yes** (to allow refunds if withdrawn) |
| `COMMISSION_REVENUE` | `PLATFORM` | `REVENUE` | `moja_ride` | Platform commission earned from ticket sales (e.g. 5% of base fare). | **No** |
| `CONVENIENCE_FEE_REVENUE` | `PLATFORM` | `REVENUE` | `moja_ride` | Convenience fee revenue earned from Paystack gateway checkouts (e.g. 2.5%). | **No** |
| `PAYMENT_PROCESSOR_FEES` | `PLATFORM` | `EXPENSE` | `moja_ride` | Merchant interchange fees deducted by Paystack at transaction time. | **No** |
| `PROMO_EXPENSE_PLATFORM` | `PLATFORM` | `EXPENSE` | `moja_ride` | Platform marketing subsidy expense recognized when promo codes or credit grants are issued/redeemed. | **No** |
| `PROMO_CONTRA_OPERATOR` | `COMPANY` | `EXPENSE` | `<companyId>` | Operator contra-revenue account tracking operator-funded discounts for reporting. | **Yes** |
| `OFFLINE_REFUND_PAYABLE` | `PLATFORM` | `LIABILITY` | `moja_ride` | Clearing liability for cash refunds owed to passengers at terminal counters. | **Yes** |
| `PROMO_LIABILITY_PLATFORM` | `PLATFORM` | `LIABILITY` | `moja_ride` | Platform liability for unspent marketing campaign pools. | **Yes** |

## 3. Balance Equations & Escrow Mechanics

For every account, the three balance fields relate as follows:

$$\text{postedBalance} = \text{availableBalance} + \text{reservedBalance}$$

### The Escrow Lifecycle (`reserveOnCredit` / `releaseFromReserve`):

```
                                [ TICKET SALE CONFIRMED ]
                                            │
                                            ▼
                    AccountingEngine.addCredit(..., { reserveOnCredit: true })
                                            │
                                            ▼
                   ┌─────────────────────────────────────────────────┐
                   │ OPERATOR RECEIVABLE                             │
                   │ • postedBalance:    +10,000 XOF                 │
                   │ • reservedBalance:  +10,000 XOF (LOCKED ESCROW) │
                   │ • availableBalance: +0 XOF                      │
                   └────────────────────────┬────────────────────────┘
                                            │
                                            │ (Bus departs, arrives, 24h passes)
                                            ▼
                               [ CRON: release-escrow ]
                                            │
                                            ▼
                   AccountingEngine:
                   1. Debit  OPERATOR_RECEIVABLE (releaseFromReserve: true)  [-10,000 from Reserved]
                   2. Credit OPERATOR_RECEIVABLE (normal)                   [+10,000 to Available]
                                            │
                                            ▼
                   ┌─────────────────────────────────────────────────┐
                   │ OPERATOR RECEIVABLE                             │
                   │ • postedBalance:    10,000 XOF (unchanged)      │
                   │ • reservedBalance:  0 XOF (ESCROW CLEARED)      │
                   │ • availableBalance: 10,000 XOF (WITHDRAWABLE)   │
                   └─────────────────────────────────────────────────┘
```

## 4. Transaction Types & Double-Entry Journal Blueprints

### 1. Paystack Card / Mobile Money Booking (`type: BOOKING`)
*Example: Passenger buys 10,000 XOF ticket with 250 XOF convenience fee via Paystack. Platform takes 500 XOF commission. Paystack charges 200 XOF processing fee.*

| Seq | Account Class | Side | Amount | Balance Effect | Note |
|---|---|---|---|---|---|
| 1 | `PAYSTACK_CLEARING` (Asset) | **DEBIT** | 10,050 XOF | `available` +10,050 | Net funds arriving from Paystack (10,250 - 200) |
| 2 | `PAYMENT_PROCESSOR_FEES` (Expense) | **DEBIT** | 200 XOF | `available` +200 | Paystack interchange fee |
| 3 | `OPERATOR_RECEIVABLE` (Liability) | **CREDIT** | 9,500 XOF | `reserved` +9,500 | Operator Net in escrow (`reserveOnCredit: true`) |
| 4 | `COMMISSION_REVENUE` (Revenue) | **CREDIT** | 500 XOF | `available` +500 | Platform commission |
| 5 | `CONVENIENCE_FEE_REVENUE` (Revenue) | **CREDIT** | 250 XOF | `available` +250 | Platform card convenience fee |

$$\sum \text{Debits} = 10,050 + 200 = 10,250 \quad|\quad \sum \text{Credits} = 9,500 + 500 + 250 = 10,250 \quad \checkmark$$

## 5. Concurrency Control & Deadlock Prevention

The `AccountingEngine.commit` implementation employs critical safeguards:
1. **Sorted Row Locks**: All modified account IDs are sorted alphabetically before locking:
   ```ts
   const sortedAccountIds = Array.from(accountUpdates.keys()).sort();
   for (const accountId of sortedAccountIds) {
     await tx.$queryRaw`SELECT id FROM "financial_account" WHERE id = ${accountId} FOR UPDATE`;
   }
   ```
   *Rationale: Prevents database deadlocks when two transactions touch the same accounts in reverse order (e.g. Account A & B).*
2. **Negative Balance Enforcement**:
   - Accounts with `allowNegativeBalance === false` (such as passenger wallets) immediately abort the transaction if `newAvailableBalance < 0n`.
   - Accounts with `allowNegativeBalance === true` (such as `OPERATOR_RECEIVABLE` or `PAYSTACK_CLEARING`) allow negative swings so refunds and chargebacks are never blocked by zero balances.
